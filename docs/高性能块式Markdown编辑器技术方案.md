## 2\.2 关键选型决策说明

### 2\.2\.1 为什么放弃Lexical

Lexical虽为原生节点树模型，天然适合块结构，但缺乏成熟的GFM双向转换体系，复杂语法（表格、脚注、任务列表、Mermaid、公式）需要自研转换层，极易产生私有格式，无法保证Typora、Obsidian等第三方编辑器无损打开，不满足本项目最高优先级的兼容性要求。

### 2\.2\.2 为什么放弃BlockNote

BlockNote虽为现成块UI封装，但采用全量DOM渲染，无内置虚拟滚动支持，无法支持十万字以上大文件流畅编辑，且上层封装过厚，无法深度改造渲染层，仅适合Demo原型验证，不适合长期自研的高性能编辑器项目。

### 2\.2\.3 为什么放弃React/TanStack Redact路线

TanStack Redact虽为React的轻量化同步运行时，语法与React完全兼容，生态成熟，但底层仍保留虚拟DOM协调机制，在高频块挂载卸载、局部输入更新场景下性能上限低于Solid；且Redact当前为实验版本，存在稳定性风险，不适合作为核心生产框架。

### 2\.2\.4 为什么采用 SolidJS 1.9.X 稳定版

本项目采用 **SolidJS `1.9.X` 稳定版**，当前在 `package.json` 和 `pnpm-lock.yaml` 中锁定 `1.9.19`。

- **渲染需求**　细粒度响应式支持块视图按需挂载和局部更新，文档编辑状态由 ProseMirror 管理。

- **生态兼容性**　第一阶段选型核验时，相关 Solid 生态依赖的稳定版支持 SolidJS 1.x。版本核验和集成取舍见[第一阶段设计](superpowers/specs/2026-11-12-onebox-foundation-design.md)。

前端依赖在 `package.json` 中固定到具体版本，更新时同步提交 `pnpm-lock.yaml`。Rust 依赖更新时同步提交 `src-tauri/Cargo.lock`。升级 SolidJS 或引入 Solid 生态依赖前，检查其 peer dependencies 并验证编辑和桌面构建。

# 三、核心架构设计

## 3\.1 整体分层架构

本项目核心设计哲学为**文档模型与视觉体验完全解耦**：内核层维护标准Markdown流文档以保证兼容性，UI层将顶层节点包装为独立块以提供Notion式体验，块仅为视觉交互概念，绝不污染原始Markdown文件。

1. **磁盘层：**标准GFM Markdown文件，纯净无私有标记

2. **Rust解析层：**负责大文件分片读取、pulldown\-cmark解析为AST、异步IO处理，避免前端阻塞

3. **内核数据层：**前端维护一份完整的ProseMirror文档模型，数据层始终完整，与DOM解耦

4. **虚拟滚动层：**TanStack Virtual负责视口计算，仅推送可见区域附近的块数据

5. **块视图层：**每个可视区内的顶层块独立挂载小型Tiptap编辑器实例，外层包裹块UI（拖拽手柄、操作菜单）

6. **序列化层：**编辑完成后通过prosemirror\-markdown将ProseMirror文档完整序列化为标准GFM Markdown写回磁盘

## 3\.2 大文件性能核心方案

采用**单文档模型 \+ 视口多视图**架构，从根本上解决大文件卡顿问题：

- 无论文档总长度为1万字还是100万字，DOM节点数量始终维持在几十到上百个，不随文档长度增长

- 块进入视口才挂载Tiptap实例，离开视口立即销毁实例与DOM节点，释放内存

- Rust层负责大文件分片加载，滚动时预加载前后少量块，超出范围的块AST可卸载，需要时重新解析

- 编辑操作仅作用于当前块对应的ProseMirror节点，不触发全文档重渲染

## 3\.3 元数据隔离机制

所有UI层状态（块折叠状态、拖拽顺序、块ID、拖拽位置等）**绝对不写入Markdown正文**，统一存储为同目录下的独立元数据文件（如`.editor-meta.json`）。该元文件可随时删除，删除后Markdown文件本身保持完整可用，在其他编辑器打开无任何异常标记。

# 四、开发约束规范

1. **禁止自定义Markdown语法：**Schema仅注册GFM原生节点类型，不新增私有Node类型

2. **禁止污染MD正文：**不得在Markdown中插入HTML注释、块ID占位、自定义容器标签

3. **视口渲染强制：**所有渲染层（编辑器、Mermaid、KaTeX、代码高亮）必须实现视口卸载机制，不得全量渲染

4. **重任务下沉Rust：**大文件解析、文件读写、大文本处理必须在Rust侧异步执行，不得阻塞前端主线程

5. **状态分层：**全局文档状态与块局部UI状态严格分离，避免局部状态变更触发全文档渲染

6. **序列化校验：**每次导出的Markdown文件必须可被至少两种第三方编辑器（Typora、Obsidian）正常打开，无格式错乱
